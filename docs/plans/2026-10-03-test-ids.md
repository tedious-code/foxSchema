# Test IDs on every control, and a catalog Playwright can use

Every button, text box, select and textarea in the web app gets a `data-testid`.
A generated catalog lists them as a tree (area → screen → control), with what
each one is, both as a document people read and as a typed module Playwright
tests import. Later, CI keeps it honest and an MCP server lets agents write
tests from it.

## Convention

`data-testid="<area>-<screen>-<control>[-<key>]"`, kebab-case.

- **area**: the feature folder (`git`, `sql`, `lokee`, `access`, `workflow`…).
  Existing short prefixes stay as they are.
- **screen**: the dialog, panel or page (`commit`, `branch-view`, `repos`).
- **control**: what it does, not how it looks (`push`, `note`, `run`), never
  `button-1` or `blue-btn`.
- **key**: for one control per row, the row's stable key:
  `git-run-${fileName}`, never an index.
- Unique within what can be on screen at once. Containers (dialogs, panels,
  lists) get one too, so a test can scope inside them.
- Existing IDs are standardized only where that helps: duplicates, and
  inconsistent prefixes. Each rename updates its e2e references in the same
  PR. New and missing IDs follow the convention.

## Phases

### A. Catalog and guard rails (1 PR)

- `scripts/test-ids/extract.mjs`: parses the web app's TSX with the TypeScript
  compiler and records every `data-testid`. For each one it records:
  - the file and component;
  - the element (button, input…);
  - whether it is static or built from data (`git-run-{fileName}`);
  - a description from the control's own words: visible text, `aria-label`,
    `title`, `placeholder`, or its `<label>`.
- Generated and committed, never hand-edited:
  - `docs/testing/TEST_IDS.md`: the tree people read.
    ```
    Migrations in Git (features/git)
    └─ CommitMigrationDialog
       ├─ git-commit-dialog      dialog      Commit migration to Git
       ├─ git-commit-note        textarea    Note (the commit message)
       ├─ git-commit-only        button      Commit
       └─ git-commit-push        button      Commit & push
    ```
  - `apps/e2e/src/generated/test-ids.ts`: the same tree as a typed module.
    Tests get autocomplete, and a removed ID is a compile error rather than
    a timeout:
    ```ts
    await page.getByTestId(TestIds.git.commitDialog.push).click();
    await page.getByTestId(TestIds.git.branchView.run('20261003__add.sql')).click();
    ```
- A test fails when the generated files are stale (the `doc-paths` test does
  the same for doc links), with the command to regenerate them.
- A **coverage ratchet**: a test fails if the number of controls without an
  ID goes up. It starts at 397 and only moves down. It is cheaper and clearer
  than an ESLint plugin, and it reuses the extractor.
- Duplicate static IDs are listed in the catalog and fixed in phase B.

### B. Fill the gaps (about 6 PRs, by area)

Add the 397 missing IDs, lowering the ratchet each time. Order follows what
e2e tests need first:
1. Auth and sign-in settings: `PasswordRecovery`, `SignInSettingsPanel`,
   `TopToolbar`, `SettingsPanel`.
2. Git and migrations: `GitReposAdmin`, `GitBranchView`, `ObjectDetailPanel`,
   `MigrationHistory`.
3. SQL editor: `TableBlueprintModal`, `SqlVariablesPanel`, the rest.
4. Workflow: `HttpRequestEditor`, `DelimitedSourceEditor`, `Inspector`,
   `TriggerInlineSettings`.
5. Utilities and access.
6. Everything left, the duplicate IDs, and the ratchet set to 0: from then on
   a control without an ID fails CI.

Each PR is UI attributes only, with no behaviour change. The extractor proves
coverage; the existing e2e suites prove nothing broke.

### C. Playwright adoption

- Page objects in `apps/e2e/src/pages` read `TestIds` instead of string
  literals, a file at a time as they are touched.
- `docs/testing/WRITING_E2E.md`: a new test in five minutes. Find the screen
  in `TEST_IDS.md`, copy the IDs, use a page object.
- `npx playwright codegen` already records `getByTestId(...)` for these
  controls, so a recorded flow is a usable first draft.

### D. Longer term: automation and an MCP server

- **CI**: the stale-catalog test already blocks drift. Add a PR comment listing
  IDs added and removed, so a reviewer sees a test-facing change.
- **Selector health**: a nightly e2e pass opens each main screen and checks the
  catalogued static IDs it should show are there. This catches an ID left on
  dead code.
- **MCP server** (`@foxschema/test-ids-mcp`, local stdio):
  - resources: the catalog as a tree;
  - tools:
    - `find_test_id(query)`: by words, so "the push button in the commit dialog" gives `git-commit-push`;
    - `describe_screen(component)`;
    - `scaffold_test(flow)`: a Playwright test skeleton built on the page objects.

  Paired with the official Playwright MCP, which drives the browser, an agent
  can find the right selectors and write a test that uses them.

## Decisions (2026-10-03)

1. **Existing IDs may be standardized** where it helps: duplicate static IDs,
   and areas whose prefixes are inconsistent. Each rename updates its e2e
   references in the same PR, and the typed catalog turns a missed reference
   into a compile error.
2. **Enforcement**: the coverage ratchet test.
3. **Catalog**: `docs/testing/TEST_IDS.md` and
   `apps/e2e/src/generated/test-ids.ts`, both generated.
4. **MCP**: decided after phases A–C, once the catalog has been used.

## Not in scope

- Renaming or restyling controls.
- `data-testid` in production builds: they stay. They cost a few bytes and
  are what support uses to reproduce a report.
- Test IDs outside the web app (CLI, desktop).
